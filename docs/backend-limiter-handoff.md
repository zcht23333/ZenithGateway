# 限流诊断口径与有界结果交接

本轮承接 [短时饱和诊断](backend-limiter-diagnosis.md)。修复的是已经确定的诊断和线程占用问题；不将 Redis 往返、JVM 恢复调度和下游准备工作的全部长尾归因于单个组件。

## 诊断口径

管理认证与 no-store 保持不变，GET /settings/rate-limit/diagnostics 只读本地状态。diagnosticSchemaVersion=2 标识本轮计数解释变化。

| 字段 | 含义 |
| --- | --- |
| commandsInFlight | 发起客户端命令后，尚未观察到 Future 结果、也未确认物理连接关闭的命令数，含恢复探测。成功或异常完成均可结束客户端等待。 |
| activeWorkers / queued | I/O 执行器的忙碌线程数 / 当前队列长度；前者可包含连接建立、等待、解析和关闭；关闭交接时还包含同步下游。它与 commandsInFlight 不再混为一谈。 |
| activeDeliveries / queuedDeliveries | 专属结果执行器正在调用同步消费者的数量 / 等待分发的已裁决结果。 |
| activeInlineDeliveries | 当前调用方或基线 I/O 线程正在同步发出结果的数量。未准入的立即放行、限流关闭等短路径不进入专属交接队列。 |
| retainedTasks / availableDecisionPermits | 仍占用共享准入名额的任务数 / 剩余名额。交接模式下，I/O 作业清理和同步消费者调用都结束后才归还。 |
| observations.reasons | 固定原因的生命周期累计计数；后续成功不会覆盖 queue_full 等历史次数。 |
| observations.rejections | admission_full 与 executor_rejected 分开计数；delivery_rejected 用于检查停机竞争或交接容量不变量异常。 |
| observations.timings | 固定 13 桶的纳秒墙钟耗时、样本数、累计值和最大值；无 IP、路由 ID、请求 ID 等无界维度。 |
| postDecisionCancellations | 已选择终局额度决定后收到的取消。原额度结果仍成立；代理完成链另外记录最终请求取消。 |

客户端观察到结果、释放连接，均不能证明上游业务没有执行，也不能证明 Redis 扣费被撤销。命令在 Redis 端已执行但回复丢失时，仍不重试、不返还令牌。

commandsInFlight 由 Future 完成回调或 get 返回触发同一个原子结束门；取消 get 本身不释放该计数。没有可用结果时，保留计数到物理连接关闭得到确认。计数不能解释成“Redis 服务器此时执行多少命令”，客户端失去连接后服务端仍可能完成已接收的命令。

耗时区分 queue、connection、redis_wait_and_resume、command_observation、decode、decision、handoff_queue、delivery、cleanup、worker_total。它们包含调度与 GC，不能作为 CPU 时间；阶段样本数独立，连接/解码未到达记录点的失败不纳入对应阶段直方图，阶段之和不是端到端请求时间。指标并发读取不构成原子快照，静止后才做精确对账。

原 Prometheus zenith.ratelimit.redis 名称为兼容保留：它测量额度结果交付前的等待，不是 Lua 执行时间。本轮将记录点移至 onNext 中、同步下游构建之前，避免把下游准备工作计入该时长。最终请求统计与审计仍由原完成链记录一次。

## 有界交接与所有权

新增启动参数 result-handoff-enabled 和 result-workers，仍在 zenith.limiter 下。默认关闭交接；显式开启后使用 2 个结果线程，合法范围 1–16。诊断修正默认生效。候选尚未通过 4000 req/s 的健康门槛，因此未将新调度模式设为默认。运行配置六字段、版本、操作回执和 Redis 桶格式均不变。

默认 profile 的 I/O 资源仍为 8 个线程、64 个排队位；capacity profile 仍为 8 / 128。500ms 决策预算、连接策略、故障放行与探测间隔不变。本轮对照固定 8 / 128 / 500ms，不通过增加这些值获取结果。

设 N = workers + queueCapacity。交接执行器是固定线程池加容量 N 的 ArrayBlockingQueue，使用 AbortPolicy，不使用 CallerRuns，也不使用共享调度器的隐藏大队列。已有准入名额同时为结果交接预留容量：每个准入任务最多产生一个交接作业，总共最多 N 个准入任务，不能把 I/O 队列与结果队列容量相加当成可接收请求数。

~~~mermaid
flowchart LR
  A[请求] --> B{共享准入名额 N}
  B --> C[有界 I/O 队列]
  C --> D[等待 Redis / 解析额度决定]
  D --> E[有界结果交接队列]
  E --> F[同步下游订阅与准备]
  F --> G[消费者返回]
  D --> H[I/O 清理结束]
  G --> I{两段均结束}
  H --> I
  I --> J[归还共享名额]
  B -->|已满| K[queue_full 单独计数并按原策略放行]
~~~

结果线程执行 sink.success 触发的同步片段，不等待整个 HTTP 响应体完成。慢消费者不再占用 Redis I/O 线程，但仍占用共享名额；它会造成可观察、有限的交接积压，并不会凭空消失。未准入请求保持既有故障放行行为，由请求调用方继续处理，不新增后台排队。

500ms 是额度裁决预算。已有明确额度结果后，不能因为后续交接变慢把 429 改成故障放行。交接等待单独测量，其有限容量不等于响应时间硬上限；事件循环及同步下游仍须遵守不阻塞的约束。系统调度暂停也可能让定时器晚执行。

取消等待 I/O 的任务先移除或中断作业，再结束结果处理；物理连接未确认关闭前不归还其物理所有权。取消已经排队的结果会移除该作业；已经选择的额度决定不撤销。停机先停止新准入、终结未裁决任务、关闭 I/O，再有界排空结果执行器；超时后中断作业并使尚未交付的订阅以取消错误结束，不静默悬挂。

关闭 result-handoff-enabled 可运行带修正诊断的同步基线；该模式保留原先裁决完成时较早释放准入名额的行为。因此 A/B 对比评估的是完整的“预留名额 + 有界交接”方案，不声称只有一次线程切换这一项差异。

## 方法依据和边界

产物实际依赖 Reactor Core 3.8.7、Lettuce 7.5.2.RELEASE。Reactor 默认沿用前一操作的执行线程，这解释了原 sink.success 后的同步调用链；见 [Reactor 官方线程说明](https://projectreactor.io/docs/core/release/reference/coreFeatures/schedulers.html)。队列容量与拒绝行为依据 [JDK 21 ThreadPoolExecutor](https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/util/concurrent/ThreadPoolExecutor.html)，容量上限另由可控测试与真实故障验证交叉检查。

### 同包 A–B–B–A 对照

A、B 使用同一候选 JAR，分别显式关闭和开启交接。每实例先预热 30 秒 × 1000 req/s、60 秒 × 4000 req/s，然后按 A–B–B–A 顺序运行四段，每段 180 秒、4000 req/s 开放模型到达。I/O 均为 8 线程 / 128 排队位 / 500ms；B 另用 2 个结果线程，共享 136 个准入名额。32 条路由，限流、监控、审计和熔断开启，补充速度与容量为 10000，单次成本为 1。仅每次被测实例收到压测流量。

两实例的所有 Redis 用途均直连同一个专属 Redis，CLIENT LIST 证据记录了实际连接来源。Docker Desktop VM 为 16 逻辑 CPU，Redis 使用 0–1、上游 2–3、被测网关 4–7、驱动 8–11；两网关使用同一组 CPU，但不同时压测。JVM 为 JDK 21.0.12.1，堆 256m/512m、直接内存 256m、G1、容器内存 1GB。完整镜像 digest、参数、采集模式、GC 日志及源文件散列在原始 summary 中。复用了诊断框架的配置字段，其中 longSeconds、soakSeconds 和 modes 不表示本轮实际执行了长稳态或六组采集实验，实际执行范围以 stages 为准。

### 兼容、清理与剩余范围

无需 Redis 数据迁移。默认部署获得诊断 schema 2，监控采集方应按新含义解读 commandsInFlight，不能与旧口径直接拼接比较。固定原因计数需要用阶段差值，峰值不能相减。已开启交接的试验部署可通过启动参数 --zenith.limiter.result-handoff-enabled=false 恢复原同步调度，仍保留诊断修正；生产/开发实例升级均需单独执行，本轮没有升级它们。

所有实验使用本轮专属容器、随机端口和命名空间。对照的网络、容器、临时凭据，两次后端集成 Redis，以及候选/最终功能验证进程均已清理。保存的源码、报告、日志、JAR 属于证据，未删除。结束时复核本轮容器、网络及进程不存在，原有六个停止或未启动容器保持原身份与状态；记录见 JSON 索引与 cleanup-check.json。

前端源码和测试未修改，本轮未重跑前端测试、前端生产构建或浏览器；此前结果不能算作本轮结果。没有重跑完整路由发布、配置同步/回执/回滚的独立长链路验收；后端完整测试与限流/代理真实回归覆盖了本轮直接影响。未执行最终 JAR 的长稳态或完整性能对照，未部署开发实例。

尚存的明确边界：交接只隔离同步下游对 I/O 工作线程的占用，仍可能因 Redis 往返、调度、GC 或同步消费者而填满共享名额；默认故障放行会继续放过 queue_full。有限队列不承诺任意阻塞消费者的交付时限，500ms 也不是整个 HTTP 请求的硬时限。未观察到队列越界不等于零积压。这里提交的是诊断修正和可选优化的实现与证据，不宣称已经解决全部尾延迟或通过 4000 req/s 长期容量验收。
