# 分布式限流正确性与 Redis 故障降级

本轮交付用于验收，现有开发实例没有升级。范围是普通 HTTP 代理的按客户端 IP 共享令牌桶；六字段运行配置、operationId、提交回执、历史、安全回滚与后台配置同步协议不变。

## 四项决策

| 决策 | 实现与代价 |
| --- | --- |
| 时间基准 | 在一次 Redis Lua 决策中调用 TIME；网关不传本机时间。每桶保存不倒退的计费时间，时间回拨期间不重复补充。 |
| 额度公式 | 用整数毫令牌计算；首次建立桶为容量上限，放行扣实际成本，拒绝也保存余额与计费时间。 |
| 配置切换 | 稳定 IP 桶键＋持久化策略版本门槛。按桶旧速度结算，再收缩至新容量、应用新成本；不因配置版本变化建立满额桶。 |
| 故障降级 | 保持放行，但限制实际物理连接、在途命令、等待队列与等待预算。关闭故障连接后才复用槽位；不自动重放不确定的扣费。 |

实现入口为 `RateLimitFilter` → `RedisRateLimiter` → `rate-limit.lua`。限流读取一次本地不可变运行配置快照；Lua 仅访问策略门槛和客户端桶，不读取运行配置、回执或历史。现有认证、可信代理 IP 解析及代理保护顺序没有改变。

## 先建立的旧行为证据

保留了任务开始时 JAR、源码备份与旧脚本。真实双实例、独立 Redis 复现了固定配置时的共享扣费，以及以下缺口：

- 原 Lua 使用调用方时间。受控时间序列 `t, t+1s, t, t+1s`，容量 2、速度 2、成本 2，在唯一时间区间只应有 4 个令牌时实际扣了 6 个。
- 原 `Retry-After: 1` 不考虑实际缺口；成本超过容量仍给出 1 秒建议。
- 原链路 HTTP 等待超时之后，12 条已排入共享连接的扣费命令仍可在故障代理释放时到达 Redis。只有 Reactor timeout 不能证明命令已经取消。

源码推断与上述实际实验分开记录。旧源码、原始运行与本轮修正后的重跑均保留；JSON 索引给出路径与产物摘要。

## 额度、时间和过期

记 Redis 毫秒时间为 `R`，桶中计费时间为 `T`，毫令牌余额为 `B`，旧容量/速度为 `C0 / r0`，本次有效容量/速度/成本为 `C / r / q`：

```text
T1 = max(R, T)
B1 = min(C0 * 1000, B + (T1 - T) * r0)
B2 = min(C * 1000, B1)
q <= C 且 B2 >= q * 1000：放行，B3 = B2 - q * 1000
其他：拒绝，B3 = B2
保存：B3、T1、本次有效策略
```

计算先限制最大可补充时间，再乘速度，避免巨大时间跳变造成数值精度溢出。令牌精度为 0.001，时间精度为 1ms。没有桶时以 `C * 1000` 初始化并立即扣费；相同客户端的所有普通代理路由共用桶，不按路由重复给额度。无法解析客户端时使用共享 `unknown` 桶；可信代理规则仍决定 X-Forwarded-For 是否参与解析。

健康的单 Redis、固定配置、桶数据未被提前删除/驱逐/丢失时，合计成功扣费满足：

```text
sum(allowed cost) <= 初始可用令牌 + r * Redis 有效计费时间跨度（秒）
```

拒绝请求不扣费，但会记录已经结算的时间，因此回拨后不会再补充同一段时间。Redis 时间大幅向前跳会按该时间增长补充，并可能触发过期；这不是独立于服务端时钟的物理时间保证。[Redis TIME](https://redis.io/docs/latest/commands/time/)

空闲桶使用 `PXAT = T1 + 10,001,000ms`。这是现有合法最大容量 10,000 / 最低速度 1 再加 1 秒的保守回收窗口；约 2.78 小时**未访问**才可回收，回拨形成的时间债会延长实际保留。每次访问刷新期限，策略门槛不设 TTL。这样速度调整不会缩短 TTL、提前再发满桶。自然过期后新桶重新获得有效策略下的完整初始容量，且旧实例仍受门槛保护。Redis 过期使用绝对时间；测试夹具只替换 Lua 的时间来源，没有修改宿主机或 JVM 时钟。[Redis 过期语义](https://redis.io/docs/latest/commands/expire/)

此选择增加 Redis 存量 IP 键的保留时间。没有新增 JVM 侧 IP 缓存；Redis 键数量随该空闲窗口内的客户端数量增长，不能宣称基数固定。部署需设定 Redis 内存预算并使用 `noeviction`；容量不足会成为故障放行，而不是悄悄驱逐桶后重置配额。数据丢失、主动删除桶、持久化丢失与故障切换回退均不在健康额度保证内。

## 异步配置采用与策略门槛

每个命名空间有一个 `:policy` 键，记录已经观察到的最高**启用限流**配置版本及容量、速度、成本。版本仍是 `UUID epoch:revision`；只在 epoch 相同的情况下比较 revision，随机 UUID 绝不按字符串排序。

- 新请求版本高于门槛：在同次 Lua 中推进门槛。低于门槛：按门槛中的参数执行，返回 `staleRequest=true`，不会写回旧策略。同版本不同参数视为损坏并降级。
- 桶第一次观察新策略时，用其保存的旧速度补齐上一段时间，先受旧容量限制，再收缩至新容量，随后用新成本决定扣费。下一段使用新速度。容量增大不会自动填满新增空间，成本降低也不会返还已扣令牌。
- **切换点是每桶实际观察新策略的那次决策**，不是配置提交时间。某桶长时间未被访问时，未观察期间仍按其旧速度结算；本轮没有建立全局配置生效时间轴。新速度不追溯重算已结算额度。
- 尚未有任何启用限流请求观察新版本时，旧实例仍用旧门槛。某实例已经观察新版后，其他旧实例的启用请求也会执行门槛的新参数；诊断中的实际决策版本可以高于该实例本地采用版本。
- 本地快照为关闭时直接旁路，不访问桶、不删除桶、不推进策略门槛。开关传播期间，一部分实例可能放行、一部分仍扣费；重新开启后从保留余额继续结算。配置保存成功不代表所有实例立即执行新开关或配额。
- 监控字段修改引起版本递增时也可以推进门槛，但不补发额度。安全回滚仍是更高 revision 的新提交，正常走上述规则。
- 不同 epoch、策略键缺失但桶仍存在、非法 JSON、错误数据类型、未知 schema 均不自动修复或清空，保留原值并暴露原因。空的独立命名空间可以由首次请求建立门槛与桶；外部删掉整个命名空间导致的重建不属于配额连续性保证。

桶 JSON 为 `{schema:2, policy:{schema:2,version,capacity,rate,cost}, tokensMilli, billedTimeMs}`，策略键保存其中的 policy。两个键在同一 Lua 内读、校验、决策、写；支持单 Redis 7.4，启动拒绝 Cluster、Sentinel 和 master-replica 配置。本轮没有实现跨分片原子性。

Lua 串行执行避免并发交错，但不是事务回滚。校验和编码在写之前完成；先写版本门槛，再写桶。若第二条 SET 中途失败，门槛可能已推进，但没有给桶增加额度；网关返回故障放行，不能宣称该请求得到正常额度确认。回复丢失时两个写入也可能都已完成。故障放行流量不受健康额度不等式约束；Redis 持久性和故障切换后永久扣费保证没有新增。[Redis 脚本执行语义](https://redis.io/docs/latest/develop/programmability/eval-intro/)

## Redis 故障时的实际资源边界

启动配置 `zenith.limiter` 独立于六字段运行配置，构造连接与线程前校验：

| 参数 | 默认值 | 接受范围 | 含义 |
| --- | ---: | --- | --- |
| namespace | `zg:rl:v2` | 1–128 个 ASCII 字母、数字、冒号、下划线、短横线 | 同一部署全部实例必须一致，环境间必须不同 |
| workers | 8 | 1–64 | 固定物理 I/O 槽位 / 工作线程上限 |
| queue-capacity | 64 | 0–4096 | 有界 FIFO；0 为直接交接，不积压等待 |
| decision-timeout-ms | 500 | 50–2000 | 从创建决策任务起，含排队、连接/握手及等待回复的总预算 |
| probe-interval-ms | 1000 | 100–30000 | 故障期间定时尝试安排一次探测 |

每个 worker 最多拥有一条已连接或正在建立/关闭的连接，每条连接同一时刻最多一个应用命令。已连上时复用，不每请求重连；工作线程上的有界 future 等待不阻塞网关事件循环。总等待使用 `System.nanoTime`，与 Redis 计费时钟职责不同；预算是尽力的调度期限，JVM 停顿会增加实际耗时，并非硬实时承诺。

独立 Lettuce 7.5.2 客户端显式关闭自动重连，断开时拒绝新命令，底层 requestQueueSize 为 8（包含握手等命令）；没有共享模板的离线积压。限流层每槽一个命令是更紧的应用上限。Future 取消本身不作为释放依据：槽位保持占用，直到连接建立结束并关闭、或故障连接 close future 完成。关闭异常则隔离该槽位，不再为它无限建立连接。[Lettuce 客户端选项](https://redis.github.io/lettuce/advanced-usage/client-options/)

还有一个专属计时线程。创建任何业务定时项前，先取得 `workers + queue-capacity` 个准入凭据之一；终态选定且定时项移除后才释放凭据。ScheduledThreadPoolExecutor 的底层延迟队列本身可增长，这里的数量上限由准入凭据直接保证：业务定时项最多 `workers + queue-capacity`，另有一项周期探测，取消项立即移除。探测与请求使用同一有界 worker 池，同时最多一项探测；独立 Netty 客户端资源使用两个 I/O 与两个计算线程。没有按 IP 扩张的本地缓存；物理连接槽位和逻辑决策凭据分别受限，释放逻辑凭据不代表连接已经关闭。

状态流转为 `unchecked → healthy → degraded/probing → healthy`。传输失败后本地故障门关闭，后续新请求立刻故障放行，不再每请求尝试 Redis。探测是无键、无写入的 `EVAL return 'PONG'`，经过同类命令路径，可以观察 `CLIENT PAUSE WRITE`；不扣任何客户端额度。探测成功只是当次传输检查通过，不保证所有桶格式正确、写权限完整或此刻 Redis 永远可用。失败世代阻止旧探测清除较新的故障。连接能够正常关闭、网络恢复且有可用槽位时，恢复目标为一个探测周期加一次决策预算（默认约 1.5 秒）；线程停顿或槽位关闭异常时不作硬实时承诺，状态继续降级。恢复后每个请求仍必须重新执行自己的额度决策。[Redis CLIENT PAUSE](https://redis.io/docs/latest/commands/client-pause/)

关闭时停止探测/定时器、结束等待任务、关闭槽位和客户端资源、等待 worker 退出。真实验收在捕获到在途命令后关闭实例，检查进程退出、Redis 客户端名称消失和 `active=0, queued=0, commands=0`。

本地容量不足、排队超时、关闭状态是在发送前放行，`execution=not_sent`。连接建立失败也可以确定该次应用命令未发送。已提交给连接但未得到回复是 `execution=unknown`；本地关闭只保证不在该客户端自动重放，**不能撤销 Redis 已接收的命令**。Redis 实际暂停实验单独记录恢复后是否出现扣费，不能把“本次没有迟到扣费”泛化为永远不会执行。调用方取消同样不能证明未扣费，更不能撤销上游副作用。

扣费只有一次 EVAL，没有重试、没有补偿返还。使用完整脚本而非 EVALSHA，SCRIPT FLUSH 不会产生 NOSCRIPT→重试分支，代价是每次发送脚本文本。审计持久化的原有重试机制职责不变；代理自动重试仍关闭。

## 429、可观察结果与审计

| 限流结果 | 转发行为 | 意义 |
| --- | --- | --- |
| disabled | 转发 | 本实例已采用关闭 |
| allowed | 转发 | 本次 Redis 原子额度确认 |
| limited | 429 | 有限额度暂时不足 |
| unfulfillable | 429 | 合法配置中成本大于容量，等待不能解决 |
| redis_fail_open | 转发 | Redis/桶异常或等待恢复，未得到正常额度确认 |
| local_fail_open | 转发 | 本地队列满、队列超时或服务关闭 |
| cancelled | 结束等待 | 决策期间客户端取消，不记正常额度放行 |

普通耗尽在 Lua 决策点计算：

```text
Retry-After = max(1, ceil(((T1 - R) + ceil((q*1000 - B2)/r)) / 1000)) 秒
```

该值包含时间回拨债务，是基于当时缺口的建议，不预留未来令牌；竞争请求和后续配置变化可能使重试仍失败。成本大于容量时不发送 Retry-After，JSON 的 `retryAfterSeconds` 为 null，`limitReason=cost_exceeds_capacity`；保持原合法参数范围不变。429 原有 `reason=gateway_limited` 继续供代理与审计识别，具体子原因使用 `limitReason` / `rateLimitReason`。

`GET /settings/rate-limit/diagnostics` 受管理认证保护，成功及认证拒绝均 no-store，仅观察本地内存、不触发 Redis。返回实例、命名空间、本地采用配置、最近实际决策、传输状态及时间、队列/在途/连接槽位、累计 outcome、探测和恢复次数。没有客户端 IP、随机请求 ID 等指标标签。诊断是并发采样，不承诺字段间的事务快照；精确对账应等待在途归零。

审计新增可选 `rateLimitOutcome`、`rateLimitReason`，最终 HTTP outcome/reason/phase 保持独立。故障放行后上游 200 仍保留故障放行标记；客户端在获得额度后再取消上游请求，限流决策仍是已完成的 allowed，最终 HTTP outcome 为 cancelled。取消与结果通知竞争时，以限流组件首先确定的终态为准，并在通知 HTTP 链路前共享给审计；因此“已确定 allowed，但 HTTP 通知前客户端取消”仍保留额度事实，HTTP 单独记录取消。订阅后立即取消也经过相同终态门，不会计成 disabled 或重复结束。每个入口只生成一次最终审计。现有 Redis 性能聚合保留其低基数结果；细分原因用本地诊断与审计查看。前端仅为新字段增加结果说明，不增加管理工作流或演示数据。

## 存量迁移与回退

运行配置、回执存储格式及写协议没有变化；桶从旧 `zg:rl:tb:<IP>` 哈希变为 `<namespace>:bucket:<IP>` JSON，并增加 `<namespace>:policy`。旧新写入端不能并存提供同一份额度：旧端不认识门槛和 schema，分开写键会形成两份初始额度。

升级流程：

1. 停止全部旧网关、代理入口和配置写入端，备份运行配置与桶数据；不要只升级某一个实例。保持此轮产物与现有开发实例隔离。
2. 确认部署命名空间、Redis DB 与权威 runtime key；使用维护工具，必须显式传 `--maintenance`，备份文件必须为新文件。
3. `migrate-v1` 按 SCAN COUNT 128 遍历旧键，逐键备份并 fsync，再用 Lua 比较原数据与权威配置原始字节后转换。余额保守向下取整至毫令牌并按现容量裁剪；不信任旧网关计费时间，不补入停机期间信用；旧键保留。
4. 启动全部新实例，检查 readiness、本地同步、限流诊断与真实代理行为后再开放流量。验收先在专属环境完成；本轮未执行开发/生产升级。

```powershell
node verification/rate-limit-storage.mjs migrate-v1 --port PORT --database 0 --namespace DEPLOYMENT_NAMESPACE --runtime-key RUNTIME_KEY --backup NEW_BACKUP.jsonl --maintenance
```

工具可指定 `--host`、`--legacy-prefix`；认证读取现有维护工具环境变量 `RUNTIME_REDIS_USER` / `RUNTIME_REDIS_PASSWORD`。工具仅支持普通 TCP，TLS 生产迁移需另行受控通道；不得为了运行工具关闭现有安全设置。

权威配置经过受控恢复改变 epoch 时，先停全部实例，保留两份备份，再执行同工具 `adopt-epoch` 模式。它保留毫令牌余额、只做新容量裁剪、计费时间取旧值与 Redis 当前值较大者，不生成满桶，也不修改运行配置/回执。未完成迁移前不恢复流量。

维护转换是逐桶受保护操作，**不是全命名空间事务**；进程中断或回复丢失可能已改写部分键，保持维护状态，通过 before/after JSONL 和实际 Redis 核实后处理。目标键已存在时 migrate-v1 拒绝覆盖；不要换备份文件无脑重跑。SCAN 允许重复返回，同样可能触发该保守拒绝，操作员应核对已经转换的键；本轮不把它描述为无人工处理的大规模自动迁移系统。

回退二进制必须同时处理桶格式：停止全部新实例；保存本轮桶及门槛；为每个当前 v2 桶和仍存在的 v1 桶建立**不增加信用**的旧格式余额（最保守可置 0），以回退时统一检查过的旧进程时间作为旧 `ts`，再统一启动旧端。不能直接启用保留的旧桶余额，它们可能已经落后于 v2 扣费。另一选择是在全停流量并确认时间没有回拨的维护窗口等待完整 10,001 秒，再接受重新建立满桶的语义。旧程序恢复后也恢复旧时间/故障局限；没有承诺回退仍具备本轮保证。现有运行配置格式回退工具与回执风险说明继续适用，不由限流工具自动触发。

需要 Java 21、Node 24、Docker 中已有的锁定 Redis 7.4.11 镜像。先运行完整后端测试并生产打包，再从仓库根目录执行：

. ./.dev/upgrade-tools/env.ps1
