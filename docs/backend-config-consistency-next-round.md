# 后端下一轮：运行配置变更一致性

日期：2026-09-26  
状态：本文件为实施前准备稿。本轮已实现并完成隔离验证，交付及边界见 [运行配置一致性](backend-config-consistency.md)。

## 1. 目标与排序

用户目标是「后端工程能力更扎实，适合求职深挖」。前端 A/B/C 是第一轮优化，不是项目整体定稿。

下一轮优先完成运行配置的并发变更与故障确认，再扩展多实例同步。路由关联查询保留为后续产品能力。已有有界审计、指标解耦、就绪门禁、告警、故障演练与性能/JFR 工具继续作为基础。

本轮可验证目标：

> 两个管理端基于同一版本修改配置，最多一个提交被接受；另一个得到明确冲突并保留草稿。服务端在并发读取、确认丢失和重启后，能说明当前保存的版本与本实例采用的完整配置。

首轮业务范围限定在 /settings/runtime 的六个字段。前端做必要的版本与冲突交互适配，整体视觉沿用现有页面。

### 基本复现场景

A、B 同时读取：补充速率 20、统计窗口 10 秒。A 将窗口改为 30 秒，先提交。B 仍持有旧表单，将补充速率改为 40，再提交全部六字段。

目标行为：B 收到版本冲突；A 的 30 秒不能静默回到 10 秒。B 可以保留自己的修改、读取最新值、核对后明确重新提交。

## 3. 设计必须回答的问题

### 3.1 一个版本对应一个完整快照

用一个不可变的运行配置快照关联版本、限流配置和监控配置。对外读取一次快照再形成响应，不分别拼接两个可能来自不同更新的对象。

保持请求处理路径读取本地快照；配置管理不应把每个代理请求变成额外的 Redis 配置查询。明确“每个请求的一次读取”和“整个系统瞬时切换”的区别。

### 3.2 有条件的写入协议

读取返回当前版本；提交携带所基于的版本。版本比较、接受新值、生成新版本必须具有同一个存储原子边界，不能用分离的 GET → Java 比较 → SET 代替。

冲突后不自动刷新版本并重复提交整个旧表单。服务器返回结构化的冲突信息，前端保留草稿并提供明确的核对过程。

需要在设计记录中固定：
- 版本字段的编码、初始值与范围；
- 读取、成功写入、版本缺失、版本冲突的响应；
- PUT 返回本次确认的版本与有效值，而不是随意读取到的另一次并发更新；
- 旧调用方的迁移方式。不能让无版本写入继续绕过保护。

实现沿用项目现有 Redis 7.4。可以比较小型 Lua 条件写入与 WATCH/MULTI/EXEC，说明所选方式的连接管理、往返次数和错误处理。Redis 官方资料说明了 [WATCH 的条件事务语义](https://redis.io/docs/latest/develop/using-commands/transactions/#optimistic-locking-using-check-and-set)和 [Lua 执行的原子性及执行期间的阻塞](https://redis.io/docs/latest/develop/programmability/eval-intro/)。

脚本应短小，写入前完成必要校验。原子执行不应被解释成磁盘持久化保证；操作失败与结果不确定仍需单独处理。

### 3.3 提交、采用与确认

需要明确三个状态：存储中已确认的配置、本实例已采用的快照、客户端当前读到的版本。

本轮要求：
- 确定写入未成功时，不把草稿发布为本地生效配置。
- 返回保存成功前，明确本实例已采用哪个版本。
- 晚到的旧回调不能把本地快照退回旧版本。
- HTTP 成功响应丢失后，可读取确认当前状态。
- Redis 成功执行但回复丢失时，不能仅靠旧内存快照宣告未写入；提供有明确来源的重新读取与收敛过程。
- Redis 无法读取时，返回明确的不可确认状态，不把旧内存值标成刚从存储确认。
- 如果其他提交已经覆盖了目标值，读取当前状态并不能证明原请求从未执行。没有操作 ID/提交历史时，只声明读到的当前状态。

是否保留 GET /settings/runtime 为本地采用状态，还是改为从权威存储读取并同步本地，必须在接口说明中选定。若分别暴露两者，名称和前端文案要能区分。

### 3.4 启动、旧数据与兼容

处理现存无版本 JSON、缺失键、畸形数据和并发初始化。旧数据迁移需有确定规则，不能在启动时无条件覆盖已有配置。

保留已有 readiness 保护：配置恢复完成前不接受代理请求，恢复失败的行为仍然可见。说明本轮的回退方式和旧版程序与新版存储格式是否兼容。

## 4. 实施顺序

1. **先复现与定约定。** 建立双窗口旧值覆盖、整体快照与确认丢失的测试；写清读取和成功响应语义。
2. **实现存储与快照。** 条件写入、完整不可变快照、返回值归属、确认与重启恢复。
3. **适配现有客户端。** 前端携带版本，冲突保留草稿；预览、脚本与测试夹具同步适配。必要时更新文档示例。
4. **独立环境验收。** 使用独立 Redis 与网关，保存原始证据，检查旧接口调用是否已迁移。

每一步围绕明确行为验证，不用增加测试数量代替证明。

## 5. 必须通过的验收场景

| 场景 | 验收结果 |
| --- | --- |
| 两个客户端持有同一版本、顺序提交不同字段 | 一个接受，另一个冲突；后者不撤销前者的修改 |
| 多个写入者并发提交同一版本 | 对不同的提交内容，仅一个提交产生新版本；冲突请求不改状态 |
| 读写并发 | 每次 API 响应中的六字段与版本来自同一个完整快照 |
| 回调和读取结果故意乱序 | 已采用版本不回退，成功响应有明确的提交归属 |
| Redis 在执行前失败 | 不发布未确认的草稿，已有配置与错误状态清楚 |
| Redis 已执行但网关未收到确认 | 与 HTTP 丢响应分开注入；重新读取存储后能收敛，不误报未写入 |
| HTTP 成功响应未到客户端 | 通过读取确认当前状态，客户端不盲目重发旧表单 |
| 确认期间又发生其他更新 | 展示最新版本与仍有差异的草稿，避免错误归因 |
| 重启、旧格式、缺失键和非法持久化值 | 行为符合迁移和 readiness 约定；不静默覆盖有效配置 |
| 前端冲突、认证失效、再次读取 | 草稿保护和原有保存状态继续成立 |
| 正常配置更新 | 运行快照、返回版本与独立 Redis 中的记录可以对照 |

需要真实 Redis 集成验证存储竞争与回复丢失；仅 mock Java 返回值不能证明 Lua 或事务的实际行为。可使用已有故障代理与隔离测试工具，修改和故障注入只发生在独立环境。

测试机制优先使用屏障、可控调度或明确的故障开关；避免通过任意 sleep 碰运气制造竞争。性能检查只测新增机制的实际开销：正常管理操作，以及代理请求是否仍只读取本地快照。

## 6. 本轮范围与后续方向

本轮解决六字段运行配置的并发写入和结果确认，不承诺所有运行中的网关实例立即同步。用多个独立存储客户端验证 CAS，不等于已经完成多实例的配置分发。

后续第二轮：多实例版本同步、实例采用状态、通知丢失后的主动核对和断线恢复。

后续第三轮可根据前两轮发现再选择：路由配置应用确认、按路由的观测与治理。动态路由的缓存刷新与运行参数的内存更新具有不同语义，应分别设计。
