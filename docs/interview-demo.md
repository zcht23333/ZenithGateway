# ZenithGateway 十分钟演示操作脚本

默认采用“已准备好的独立控制台＋只读历史证据”。控制台展示管理操作；Redis 回复丢失、资源饱和和一小时负载使用明确标注的归档。现场不重跑完整发布矩阵。项目介绍在[面试指南](interview-guide.md)，技术追问在[回答提纲](interview-questions.md)。

## 演示前准备

在自己新建的 main 源码副本和独立 Redis 中准备，并记录实际提交及启动包哈希。已验收功能基线来自候选提交 `f1c6a19e88e16603d413c07a74b98bb965878482`；main 已包含新增的证据速查脚本。速查展示各自明确标识的历史包，不会访问运行实例，也不会把历史结论改写成当前 main 的实测结果。

已准备好的环境应包含：独立端口、专属 Redis、测试口令、一个只读的受控上游，以及一条能返回固定文本的演示路由。按[启动指南](development-guide.md)建立环境。`dev.ps1` 可以复用已有 Redis，故必须先确认端口归属；不要直接使用开发实例的 Redis 或清键初始化。重新构建的 JAR 记录自己的 SHA256，不标成 CI 下载原包。

在演示副本中预检，示例端口需先确认未占用：

```powershell
.\dev.ps1 -CheckOnly -BackendPort 18081 -FrontendPort 15173 -RedisPort 16389
# 仅在确认这三个端口和 Redis 均属于演示环境后启动。
.\dev.ps1 -BackendPort 18081 -FrontendPort 15173 -RedisPort 16389
```

在新增材料所在仓库预先运行：

```powershell
node verification/interview-evidence.mjs
node verification/interview-evidence.mjs --case config --json
node verification/interview-evidence.mjs --case limiter
node verification/interview-evidence.mjs --case capacity
```

这些命令只读仓库内的归档，无需 Docker、网关或网络。输出是历史实验事实，不是当前环境健康状态。需要复跑故障矩阵时，另按[统一验收](release-acceptance.md)申请足够时间并使用新输出目录。

## 配置冲突的确定步骤

演示只修改统计窗口和令牌补充速度，不提高请求负载。

1. 在专属环境先把统计窗口设为 10 秒、补充速度设为 20，其他四项记录下来。若这恰好就是当前值，先把窗口改为 11 秒保存，再改回 10 秒保存，确保得到一条成功历史 H。保留 H 的完整版本和 operationId；初始化本身不会生成可恢复历史。
2. 打开正式 `/settings` 的两个标签页 A、B，分别读取，确认完整版本相同。它们是两个管理端，**不能用这一步声称双网关同步已得到证明**。
3. 在 B 把补充速度改为 40，先保留草稿。在 A 将统计窗口改为 30 秒并保存。记下 A 的新版本及回执。
4. B 不点击刷新，直接保存旧基准下的草稿。预期出现版本冲突；40 的草稿保留，窗口变化与待核对基准可见。
5. 在 B 点击“重新读取”，核对窗口 10→30 和待保存速度 40。点击“已核对，允许再次提交”后再保存。新提交使用新的 operationId，仍检查版本。
6. 查看服务端确认的 30 秒与 40，不声称保存成功意味着全实例同步。双实例采用与业务效果用归档 `config-sync`、`config-rollback` 的实际记录说明。

若 B 没有冲突，先检查两个标签页的完整基准版本及是否提前刷新，保留网络记录。停止这一段，转到归档中的 `config.conflict`，明确说明现场演示没有得到预期结果，不临时改 Redis 制造界面。

## 历史恢复与结果确认

1. 在 B 打开“提交历史 / 安全恢复”，选择之前的 H。逐项核对当前六字段与历史目标、当前版本、来源版本及记录时间。
2. 若当前还有草稿，先说明它不会自动成为恢复内容；保留或明确丢弃后继续。勾选核对项，再点击“确认恢复完整配置”，阅读确认框。
3. 成功后观察版本继续增加，窗口回到 10、速度回到 20，其他四项与 H 相同。新历史和回执带有恢复来源。版本号以现场实际值为准，不强行套用 18→19。
4. 在回执区域指出 operationId 和恢复来源，展开“存储已确认版本”查看当前完整版本。若要展示原回执的 `receipt.after.version`，点击“查询本次提交结果”并查看浏览器网络响应；不能把后续读取的当前版本当作原操作版本。按 `--case config --json` 查看历史 `replyLoss`：原操作成功事实与后续版本分别存在。现场没有注入回复丢失，就只讲解归档，不切换页面模拟一个真实故障。

遇到认证失效，重新输入演示凭据并检查草稿仍在。结果未知时保留原 operationId，查询该次提交；不要换 ID 连点保存。正在保存时等终态；取消离开与明确丢弃的含义不同。

## 限流证据的讲法

速查中的两行来自同一类真实故障：Redis 已执行扣费，回复被截断。默认策略记录 `redis_unconfirmed / forward / unknown`，上游收到请求；严格策略记录 `redis_unconfirmed / reject / unknown`，保护性 503 且上游未收到请求。

先指出事实，再指出动作，最后看 HTTP 与上游接收。`unknown` 与 `forward/reject` 不互斥，不能相加当请求总数。该归档使用小队列和明确故障预算来触发边界，不能当作默认配置的容量样本。需要更多细节时打开 `--json`，对应源文件和退出前资源数都在输出中。

## 无运行环境时的备用路径

使用[早期控制台录屏](media/stage-c-product-demo.webm)介绍交互，并先说明它属于阶段 C 的旧版本；它不能证明后续版本冲突、回执和回滚功能。随后直接展示速查中的原始归档，照上述时间顺序讲解，整场命名为“历史证据演示”。

仓库的 `/overview/preview`、`/routes/preview`、`/settings/preview` 是隔离演示数据。可用于介绍布局，但不用于证明真实存储、双实例一致性或故障行为。

## 开场前与结束后核对

- 候选提交、实际启动 JAR 哈希及预检结果已保存；浏览器标签注明独立环境，口令不进入录屏或终端输出。
- A、B 的基准版本相同；成功历史 H 可用；路由指向无业务副作用的测试上游。
- readiness 通过后实际发一条只读请求核对路由；低流量演示不承诺冷启动容量。
- 归档命令已通过；RSS 图片、失败记录和备用录屏已在本机打开。
- 演示结束后保存当前结果，退出自己启动的进程。启动器可能保留专属 Redis 容器和数据卷，先核对所有权再决定保留或清理，不使用全局 prune。
- 本轮新增材料只做证据读取与讲述准备；现场步骤需在面试前自行完整排练一次，不能把这份操作脚本当作新一轮浏览器验收记录。
