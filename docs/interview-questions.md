# ZenithGateway 面试追问与回答

先用每题的第一段回答，再根据追问展开到实现与实验。回答中的版本、时限和容量都有适用条件；完整介绍见[面试指南](interview-guide.md)。代码路径均可从仓库直接进入。

## 配置发布与操作身份

### 为什么 AtomicReference 还不够

它解决本实例一次读取看到完整六字段快照的问题，不能阻止另一个实例覆盖 Redis。存储并发由 expectedVersion 和原子条件发布控制；跨实例传播由后台同步完成。三个机制分别对应本地一致读取、存储竞争和异步采用。

可以画出 A、B 同读 V，A 写成 V+1，B 提交 V 被拒绝的时序。不能把本地引用发布称作分布式事务。[本地采用实现](../backend/src/main/java/com/zch/config/GatewayRuntimeProperties.java) · [快照](../backend/src/main/java/com/zch/config/RuntimeConfigSnapshot.java)

### Lua 为什么能让配置与回执一起发布

Lua 让检查和发布决策不被其他 Redis 命令插入，但脚本中途错误不会自动撤销已经执行的写命令。本项目先校验、生成并编码完整配置、回执与历史，以及要返回的响应，然后执行唯一 SET；SET 之后不再编码或执行其他写命令。

因此 SET 前失败不改变文档，SET 明确拒绝不产生半份回执；SET 成功但丢回复属于无法确认。这个结论不等于 Redis 已落盘，也不覆盖主从切换后数据丢失。[原子脚本](../backend/src/main/resources/runtime-config.lua) · [故障与持久性边界](backend-config-operations.md)

### 为什么不用 WATCH 或数据库

现有权威存储就是 Redis，数据和变更频率均有界。Lua 可以在一次决策里查操作、核对版本并发布文档，调用路径容易注入故障验证。WATCH 也能实现乐观并发控制，但要处理连接上的事务状态和竞争失败后的重试协议。

这不是证明 Redis 总比数据库合适。若需求变成长期审计、大量操作记录或更强持久性，就应重新选择存储；现有单文档每次重写的成本也会变得明显。[一致性方案](backend-config-consistency.md)

### 当前值与草稿相同为什么不能确认原提交成功

相同值可能由其他管理端写入，原操作之后也可能又有更新。查询当前值只能确认某个时刻的状态。operationId 对应的是原操作基于哪个版本、产生哪个新版本的事实，才能回答那次提交是否成功。

查询到旧成功回执不能把当前配置基准退回旧版本；查不到可用回执仍是 unknown，可能尚未执行、已过期或数据丢失。[管理接口](../backend/src/main/java/com/zch/config/RuntimeConfigController.java) · [前端状态](../frontend/src/settings/editor.ts)

### operationId 与版本号有什么区别

expectedVersion 防止覆盖别人已经提交的状态，operationId 标识一次逻辑操作。普通修改绑定类型、预期版本和规范化六字段；恢复绑定类型、预期版本和历史来源。相同 ID 换内容会被拒绝。

相同请求重试复用原 ID；变更内容、预期版本或冲突核对后再次提交要生成新 ID。已成功重试先返回原回执，即使当前已有后续版本也不重写。[操作协议](backend-config-operations.md) · [恢复绑定](backend-config-rollback.md)

### 为什么不承诺永久幂等

回执保留 24 小时，最多 512 条活动记录；容量满时拒绝新操作，不能提前淘汰仍在保证期内的回执。成功历史最多 100 条、7 天，与幂等窗口分开。有效回执内原样重试不续期。

这些保证依赖权威键保留和受控写入。键被删除、Redis 数据丢失或运维恢复后，不能继续声称原操作永久 exactly-once。窗口外应核对现状并明确发起新操作。[保留策略](backend-config-operations.md)

### 回滚为什么不把版本改回旧值

恢复的是历史提交完成后的六字段，操作顺序仍向前。例如当前 18，恢复来源 12，生成 19；新回执记录来源和恢复前后值。服务端在原子决策中核实来源，不接受前端缓存的历史参数。

预览不锁定历史；确认前来源过期或被裁剪，新恢复明确拒绝。已有成功恢复则先识别有效回执，来源后来消失也不能否认那次成功。[恢复接口和顺序](backend-config-rollback.md)

### 三秒同步是否是硬保证

不是。默认每轮完成后再等 2 秒，单次预算 1 秒，过期阈值 10 秒。约 3 秒是 Redis 正常、读取和调度停顿较短时的验证目标；仅按最坏读取预算估算就可能超过它。后台最多一个读取在途，失败不排队积累。

运行期失败保留最后有效快照，诊断显示 failed/stale。同世代只前进，同版本异值与跨世代拒绝；随机 epoch 不能按字符串比较新旧。验证 B 必须用本地 adopted/sync 观察，不让管理 GET 帮忙采用。[同步协议](backend-config-sync.md)

### 路由列表更新为什么不等于转发生效

Redis 发布和刷新事件都不能证明请求匹配已经使用新路由。路由发布采用独立版本，完整构建成功后才切换实际路由集合，并将采用版本与它绑定；失败保留旧集合，旧构建不能覆盖新版本。

切换前已经匹配的在途请求可以按旧路由完成，新匹配使用新集合。验收向受控 V1/V2 上游发真实请求交叉核对，不能只检查自定义 adopted 字段。[路由发布](backend-route-publication.md) · [路由服务](../backend/src/main/java/com/zch/route/DynamicRouteService.java)

## 限流故障与资源保护

### 两实例怎样使用同一个时间与额度

同客户端桶在 Redis 的一次原子决策内读取服务端 TIME。计费时间取 `max(Redis 当前时间, 上次计费时间)`，回拨不让它倒退；固定策略下补充量由实际经过时间乘速度得到，再截到容量，允许时扣一次成本。

实现使用毫令牌精度。拒绝也保存计费状态，成本大于容量时明确 unfulfillable，不给不可能兑现的 Retry-After。空闲桶保留到所有合法参数都足以回满的统一时间上界之后，避免配置变化缩短 TTL 重新获得满桶。额度保证限定于已验证的单 Redis 权威和键正常保留条件，不扩展为 Redis Cluster 或故障切换保证。[令牌桶 Lua](../backend/src/main/resources/rate-limit.lua)

### 热更新会不会让旧实例把桶改回去

同一限流命名空间有持久策略屏障。同世代遇到旧版本请求时按已经观察到的新策略处理，不能把屏障或桶策略回退。切换时先按桶的旧速度结算到切换时刻，再按新容量截断，之后使用新策略；升容量不会直接补满已有桶。

配置保存与实例采用仍异步，未观察新版的桶存在传播窗口。关闭限流的实例会显式绕过，不能宣称全实例瞬间执行同一配额。跨 epoch 走受控恢复，不能比较随机字符串大小。[热更新语义](backend-rate-limit-reliability.md)

### 429 和保护性 503 怎样区分

429 表示原子决策明确额度不足或成本不可满足。保护性 503 表示限流资源不可用或额度未确认，且相应启动策略选择 reject。两项策略默认 allow，分别控制本地故障和 Redis 未确认，不能用一个泛化 error 指标判断是否故障放行。

另外记录 event、action、execution 和最终 HTTP／审计。Redis 已扣费但丢回复时，严格策略的 503 也会伴随 unknown；上游零接收与 Redis 是否扣费是两件事。[决策模型](../backend/src/main/java/com/zch/ratelimit/LimitDecision.java) · [故障策略](backend-limiter-failure-policy.md)

### 为什么加 Mono.timeout 不等于资源已经有界

上层停止等待不代表底层命令消失，客户端可能有离线缓冲、连接重连或迟到回复。因此还要限制准入、队列、真实命令和结果交接，确认物理关闭，并观察恢复探测。请求超时本身不能提前把命令计数归零。

默认资源是 8 个工作线程、64 个等待名额、500 ms 决策预算，结果交接关闭；历史容量实验的等待名额是 128。不能混用不同配置下的结论。故障期间允许一个被识别且有界的恢复探测，并不允许业务任务残留；健康恢复仍需满足归零门禁。[客户端](../backend/src/main/java/com/zch/ratelimit/RedisRateLimiter.java) · [探测验收修正](showcase-validation-fixes.md)

### 为什么回复丢失不自动重试或退还令牌

命令可能已经执行，盲重试会重复扣费，返还可能创造额度。当前协议保留 unknown，并依据故障策略处理请求。只有明确未执行的情况才按协议处理，例如可识别的脚本缓存缺失；不能把所有异常都当成未执行。

代理业务请求也关闭自动重试；上游已执行写入但丢回复，不代表业务没有发生。审计后台的有界重试属于另一个协议，不能推广到业务写请求。[限流可靠性](backend-rate-limit-reliability.md) · [代理重试边界](backend-proxy-resilience.md)

### 命令计数竞态如何被确定性复现

旧实现先把 waiting 标志改成 false，再更新诊断，最后减在途数。把第一个回调暂停在标志修改之后，重复观察者就能返回并派发下一条命令，造成实际仅一条等待、计数却为 2/2。

修复让 waiting 判断、扣减和退役标志发布在同一命令对象的短临界区内完成。重复观察者等结算完成后才继续；锁中没有 I/O 或下游处理。相同夹具旧包 2/2、新包 1/1；超时和取消等到结果观察或物理关闭再退役。整个诊断 JSON 仍不是原子快照。[计数时序及测试](backend-limiter-command-counter.md)

## 代理完成与运行证据

### 部分响应已发出后还能返回新的 504 吗

不能。响应未提交时可以按连接错误、超时或熔断拒绝返回 502、504、503；已经开始发送时只能按协议中止，不能覆盖状态码或往原响应追加错误 JSON。因此 `status=200` 可以同时有 `outcome=error`。

本轮收尾还发现 Linux 上游 reset 被框架按下游断连吞掉。修复保留上游客户端异常身份及 cause，并通过真实 Web 适配层回归；同夹具旧实现有两项失败，修复后通过。[断连修复](showcase-proxy-reset-fix.md) · [回归夹具](../backend/src/test/java/com/zch/proxy/CommittedUpstreamFailureTest.java)

### 退出超时与客户端取消同时发生，记哪个结果

先让 Reactor 的终态竞争决定超时是否真正胜出，再设置 shutdownForced。即使超时已进入回退，只要最外层随后收到 CANCEL，最终 outcome 仍应是 cancelled；reason 可以保留 shutdown_deadline 说明归因。

只设置一个“强制退出”标志不足以替代终态分类。完成统计在外层处理器的 doFinally 中，并用一次性记录保护避免降级转发重复计数。取消也不能撤销上游副作用。[完成记录器](../backend/src/main/java/com/zch/monitor/RequestCompletionRecorder.java) · [取消补修](backend-traffic-lifecycle-fallback-cancel-fix.md)

### readiness 通过能立即接满负载吗

readiness 表示必要配置和路由已恢复，不能证明连接池、JIT 和线程调度已在目标负载下稳定。因此接流量分阶段，按实际失败计数、延迟、积压和对账决定是否继续；出现退化暂停提升。

真实滚动替换还需要外部负载均衡器摘除传播及在途排空。项目有对应历史验证，但不把发生器权重调整冒充产品内置流量调度，也不把一次短测称为稳定容量。[生命周期](backend-traffic-lifecycle.md) · [HAProxy 替换](backend-rolling-replacement.md)

### 一小时容量通过具体证明什么

证明指定 JAR、资源和小响应负载下，该小时同时满足已声明的 HTTP、限流、到达缺口、延迟及审计门禁。计划 360 万到达，实际 3,599,568 次 200，缺口 432；没有把未发出的请求从计划中隐去。

P95/P99 为 3.869/5.555 ms，最大 472.063 ms。结论仅属于 `3f73c65c…`，不表示最大吞吐、复杂业务性能或新候选也跑过一小时。计数夹具、故障组数和真实请求数各有含义，不合并成夸大的测试总数。[容量与 RSS](backend-rss-investigation.md) · [原始证据](evidence-index.md)

### RSS 不下降为什么不能直接判泄漏

heap used 是已使用堆，committed 是 JVM 已承诺的区域，RSS 是驻留物理页，cgroup 还包括容器范围的其他计费；NMT committed 也不是 RSS，不能把这些数相加。释放对象不等于操作系统立即收回驻留页。

正式窗口 RSS 约 584.98→617.73 MiB，年轻代 GC 后堆占用 39→57 MiB；这不是精确存活集。独立停流诊断的 trim 使其他匿名 RSS 降约 103.75 MiB，支持分配器保留页；之后仍回升，不能因此宣称自然稳定或排除泄漏。下一步最小实验是固定条件下比较自然完整标记／混合周期后的占用，必要时单列停流诊断。[RSS 分析](backend-rss-investigation.md)

## 不知道时怎样继续讨论

用“已观察到什么、目前能保证什么、还需要怎样验证”组织回答。例如：“单 Redis 范围内配置和回执共同发布；故障切换后的持久性没有纳入这项保证。若要支持，需要先定义可接受的数据损失，再验证复制、持久化和恢复后的操作身份。”不要把尚未实现的方案描述成项目能力。
