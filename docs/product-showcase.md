# ZenithGateway：从观察到变更确认

ZenithGateway 是面向 Java 后端与平台工程师的 API 网关项目：用一套控制台观察全局流量、理解路由配置、调整运行参数，并核对服务端实际确认的结果。后端基于 Java 21 / Spring Cloud Gateway，前端使用 Vue 3、TypeScript 和 ECharts。

面试使用：[项目介绍与简历段落](interview-guide.md) · [十分钟操作脚本](interview-demo.md) · [技术追问与回答](interview-questions.md)。只读证据速查：`node verification/interview-evidence.mjs`，输出明确区分功能归档、展示候选与历史容量包。

这份展示的重点是把系统能力解释清楚。概览以实际时间、QPS 和 P95 趋势组织画面；路由页将入口、限流、重写、熔断与目标按真实执行关系展开；配置页区分当前值、草稿和服务端确认。深石墨画布用于判断，黄绿色用于操作焦点，浅色区域用于逐项阅读。

## 三个后端案例

完整讲解见[工程案例](backend-case-studies.md)，每项按“问题 → 取舍 → 实现 → 故障验证 → 剩余边界”展开：

| 案例 | 建议展示的证据 | 关键判断 |
| --- | --- | --- |
| 配置一致性、幂等提交与安全回滚 | 同版本冲突、丢回复后的原操作回执、恢复生成新版本 | 当前值不能证明原操作成功；存储确认与实例采用分开 |
| 限流故障策略、资源上限与请求对账 | 429 与保护性 503、上游零接收、扣费 unknown、恢复排空 | 事实、动作、最终请求结果不是同一维度 |
| 容量校准、计数竞态与 RSS 归因 | 旧 2/2 与新 1/1、固定包一小时、堆/匿名页与单次 trim | 先修测量口径，再解释资源；容量通过不等于内存稳定 |

取消/排空两次竞态和真实 HAProxy 替换仍可作为追问材料：[退出协议](backend-traffic-lifecycle.md)、[超时仲裁补修](backend-traffic-lifecycle-p2-fix.md)、[回退期间取消](backend-traffic-lifecycle-fallback-cancel-fix.md)、[实际 LB 替换](backend-rolling-replacement.md)与[录屏](backend-rolling-replacement-demo.webm)。这些材料各自保留当时的包与失败记录，不冒充当前候选全部重新执行的结果。

## 别人如何运行和复验

[README](../README.md)提供启动和架构；[开发指南](development-guide.md)保留认证、接口与迁移步骤；[统一验收](release-acceptance.md)区分提交层与真实发布矩阵。正式页面读真实接口，preview 页面清楚标注演示数据，不用历史记录冒充实时追踪。

[证据索引](evidence-index.md)内的容量摘要、原始 GC/NMT/smaps 和计数夹具结果可以直接从仓库访问或解压，不要求访问作者的本机路径。原始 gzip 与投影摘要分开标记。当前干净候选的提交、CI 和新包身份见[发布记录](showcase-release.md)。

**单实例、4 个逻辑 CPU、1 GiB、小 HTTP 响应条件下，1000 req/s 一小时容量窗口通过；长期内存稳定性仍未证明，4000 req/s 一小时未通过。**

该小时结果属于修复包 `3f73c65c…`，不是任何新构建包自动拥有的性能标签。3,599,568 次 200、P95/P99 3.869/5.555 ms，最大值 472.063 ms，故障放行/保护性拒绝/扣费未知为零；资源、发生器缺口和审计对账随证据一起公开。结果交接默认关闭。RSS 原生回收属于单独诊断，不能证明自然平台。

## 录屏的范围

录屏使用独立网关、Redis 和测试上游，显示环境标记。986 次 HTTP 200 与 23 次 HTTP 500 均来自实际测试代理请求；这些小规模请求用于演示，不是吞吐压测。写入与真实指标来自后端，顶部环境和步骤文字只是录制说明层。测试结束后恢复配置并清理独立资源。

本项目没有用无来源的健康评分、逐路由指标或任意历史区间填补界面。P95 超范围只表示 > 60,000 ms；未保存草稿只保留在当前页面内存中。这些边界与实现能力一起展示。
