## 三十秒介绍

> ZenithGateway 是一个基于 Java 21 和 Spring Cloud Gateway 的实验网关。我围绕三个方面完善它：配置并发修改与结果确认、Redis 故障下的限流决策，以及请求和资源生命周期的准确记录。项目有管理控制台，也有真实 Redis、双实例和故障注入的验证入口。展示时我会把存储提交、实例采用和实际转发结果分开解释，并给出对应版本的证据。

## 三分钟介绍

> 这个项目面向需要动态管理路由和运行参数的场景，底层使用 Spring Cloud Gateway，Redis 保存权威配置并提供跨实例令牌桶，控制台展示流量、路由和配置变更。
>
> 第一个重点是配置一致性。两个管理端读取同一版本后提交整张表，后提交的一方可能覆盖先前修改。因此我把版本和六个参数组成完整快照，在 Redis 的同一次 Lua 决策中检查预期版本，再发布新配置。各实例后台同步到本地，普通代理请求不额外查询配置。保存成功确认的是存储事实，其他实例仍然异步采用。
>
> 随后处理了回复丢失的问题。只读取当前配置，无法证明原来的提交有没有执行，所以每次逻辑提交都有 operationId；固定请求的回执与配置一起发布。安全回滚也作为新操作：由服务端核实历史来源，把旧参数提交成递增的新版本。这样并发保护、幂等和历史追溯可以一起工作。
>
> 第二个重点是限流故障。额度不足返回 429；本地饱和和 Redis 无法确认额度则由两项独立策略决定放行还是保护性拒绝。回复丢失后，令牌可能已经扣除，所以不能盲目重试或返还。验证时同时核对入口结果、上游接收、限流决策和审计，并观察连接、队列和在途命令是否释放。
>
> 第三个重点是测量本身的可信度。容量实验发现过命令计数短暂虚高，我用受控回调顺序稳定复现，再修正终态结算。之后单独分析 RSS，区分堆占用、驻留页和原生分配器保留。历史实测包在固定条件下通过 1000 req/s 一小时容量窗口，但长期内存稳定性仍未证明。这些限制和失败记录都保留在仓库里。

## 简历项目段落

**ZenithGateway｜响应式 API 网关与可靠性验证项目**

Java 21、Spring Cloud Gateway、Reactor、Redis、Vue 3、Prometheus、Grafana。

- 完善运行配置的版本条件发布、操作幂等回执与安全回滚；通过完整快照和后台同步区分存储确认、本地采用及多实例传播，覆盖并发冲突、回复丢失和重启恢复。
- 实现 Redis 时间驱动的共享令牌桶与有界客户端资源管理，支持本地饱和和 Redis 未确认两类独立故障策略；通过真实故障验证 429、保护性 503、扣费未知及上游接收／审计对账。
- 建立包含产物身份、失败证据和清理结果的统一验收，定位并修复在途计数竞态；固定历史包在单实例、4 个逻辑 CPU、1 GiB、小响应条件下通过 1000 req/s 一小时验证，保留 RSS 稳定性未证明的结论。

面试官追问“性能提升多少”时，回答实际测得的容量与条件。两个短窗口没有证明统计显著的提升；1000 req/s 是已验证档位，不是系统最大吞吐。

## 性能表述与证据身份

**单实例、4 个逻辑 CPU、1 GiB、小 HTTP 响应条件下，1000 req/s 一小时容量窗口通过；长期内存稳定性仍未证明，4000 req/s 一小时未通过。**

该小时仅属于 `3f73c65c7c29933549878c570a6b5a8b7bd8bafad2e5333603eee1de089da838`。条件包括 32 条路由、无 TLS、单客户端桶、Redis 无持久化、监控和审计开启、结果交接关闭。实际 3,599,568 次 200，计划到达缺口 432，P95/P99 为 3.869/5.555 ms，最大 472.063 ms。展示候选没有追加一小时实验。[证据索引](evidence-index.md)保留原始材料和重新分析方法。

## 练习顺序与完成标准

1. 第一遍只讲三分钟介绍，录下自己的声音；删去无法用一个具体请求解释的术语。
2. 第二遍按演示脚本完成配置冲突与恢复，计时到十分钟以内；能在原始记录中定位一次 unknown。
3. 第三遍从追问表任取八题，每题先用三十秒回答，再指向代码和证据；至少能画出原子发布及计数退役的时序。
4. 最后练习中断：听到“为什么”“失败怎么办”时停下预设讲稿，回答该问题；不知道的点明确说明当前边界和最小验证办法。

准备完成的标准：脱离讲稿可以说明一次并发冲突、一次已执行但丢回复、一次计数竞态；能找到失败与通过的证据；不会把历史实验、当前运行界面和未执行检查混为一谈。
