# 依赖升级性能与可靠性验收（2026-09-23）

**新平台的功能与目标负载可靠性验收通过；性能结果存在明显波动，不能确认无回退。**

本次保留 30 个性能样本（旧版 12 个、新版 18 个）和正常停机、强制终止、丢响应三个生命周期探针。所有性能样本的 HTTP 状态均为 200，传输错误、监控／审计对账差额、保留记录 ID 重复和采样失败均为零。

三次各 5 分钟的新版持续负载共确认 **2,691,660** 条审计记录，丢弃和结果不确定均为零。发生器未发出的 8,340 个计划请求另行统计，不能计入成功请求。

## 环境与口径

13th Gen Intel Core i5-13500H，16 个逻辑处理器，Windows 10.0.26200。发生器、上游、网关 JVM 与 Docker Redis 共用一台主机。新旧应用均使用 Microsoft OpenJDK 21.0.12.1+1、Node 24.21.0、Redis 7.4.11；JVM `-Xms256m -Xmx512m`。每个样本新建 JVM，预热 15 秒；闭环并发 16、测量 30 秒。持续负载目标 3000 req/s、在途上限 256、每次测量 300 秒。

旧应用为 Boot 3.2.4，新应用为 Boot 4.1.1 / Cloud 2025.1.3 / Gateway 5.0.3。源 JAR、压测脚本和原始报告的 SHA256，以及每个样本的完整汇总见[机器可读报告](dependency-upgrade-2026-09-23.json)。迁移、依赖扫描、工具链与回退见[实施报告](../docs/dependency-upgrade-execution.md)。

测量前后均排空队列，核对请求数、监控完成数和审计入口数，并核对 `received = persisted + dropped + uncertain`。Redis List 只保留最近 5000 条，完整计数采用写入确认；保留记录的 ID 无重复，完整去重由集成测试和丢响应探针另行验证。资源峰值来自约每秒采样，并非瞬时上界。

**验收决定：采用新平台作为开发基线，接受已记录的性能不确定性；不宣称性能提升或无回退。** 功能、旧数据兼容、故障语义和实际约 3000 req/s 的持续负载均已验证。要作生产容量承诺或简历中的性能增益声明，需先在独立、受控环境中复验，届时再决定是否需要分配器、线程配置或热点代码优化。

## 新版故障注入

每项测量一次，作为迁移后的功能回归，不用于推断稳定容量。

| 注入 | req/s | P95 ms | 已确认 | 明确丢弃 | 结果不确定 | 待写峰值 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 仅审计回复延迟 50 ms | 3891.9 | 7.27 | 65,918 | 50,846 | 0 | 11,881 |
| 全部 Redis 回复延迟 50 ms | 258.5 | 64.13 | 7,760 | 0 | 0 | 32 |
| 审计断连 12 s，容量 256 | 4820.4 | 5.05 | 84,419 | 60,126 | 94 | 256 |

审计连接延迟 50 ms 时，后台写入能力低于输入速率，达到 16 MiB 预留字节预算后拒绝新事件；仅审计断连 12 秒时，待处理峰值为 256，超时且无法确认的批次计入 uncertain。恢复后均能排空并继续写入。全部 Redis 延迟 50 ms 会同时拖慢限流。故障场景中的丢弃和结果不确定符合现有设计边界。

## 生命周期与低流量

正常停机探针在存在 200 条待写事件时关闭应用，约 4.8 秒完成排空，231 条全部保留，退出码为 0。强制终止探针中 201 条仅保留 11 条，190 条未写入，确认内存队列不能承诺崩溃零丢失。真实 TCP 丢响应探针在 Redis 已提交后扣留响应，触发一次重试，最终两条记录各保留一次。30 次低流量可见性测量的 P95 为 39.59 ms。

## 复现与保留证据

通用运行步骤见[压测说明](README.md)。旧版 JAR 来自升级前实际工作区快照，位于本机 `.dev/upgrade-baseline/baseline.jar`；它没有提交到 Git，迁移工作区时应连同快照另行保存。新机器需要使用清单中的相同维护版运行时。交替对照的关键参数如下：

```powershell
$env:BENCH_SCENARIOS = 'rate-limit-audit,forward-only'
$env:BENCH_REPETITIONS = '1'
$env:BENCH_DURATION_SECONDS = '30'
$env:BENCH_WARMUP_SECONDS = '15'
$env:BENCH_CONNECTIONS = '16'
$env:BENCH_ARRIVAL_RATE = '0'
$env:BENCH_REDIS_PORT = '16379'
foreach ($variant in @('old', 'new', 'new', 'old', 'old', 'new')) {
    $env:BENCH_JAR = if ($variant -eq 'old') {
        '.dev/upgrade-baseline/baseline.jar'
    } else {
        'backend/target/zg-1.0.0.jar'
    }
    node benchmarks/run.mjs
    if ($LASTEXITCODE -ne 0) { throw 'Benchmark failed' }
}
```

切换回持续负载时清除 `BENCH_JAR` 和显式 `BENCH_CONNECTIONS`，再按压测说明设置到达率与时长。本次原始结果保存在忽略的 `benchmarks/results/`，每秒样本仍在原文件；可提交的 JSON 保留全部测量汇总、执行顺序与原始文件校验值。

这些测量来自共享开发主机，不能直接作为生产容量或统计显著性结论。未修改主机电源策略、停止用户程序或调整分配器、线程数来迎合结果。远程 GitHub Actions 尚未执行；Windows 的后端 83 项、前端 10 项测试与实际浏览器、启动脚本验收已经完成。
