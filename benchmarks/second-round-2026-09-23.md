## 实现

请求完成记录移到整个 HTTP 处理器之外，能够观察异常处理与 fallback 后的状态，并只记录一次；取消和未形成响应的请求有明确 outcome。监控独立于审计，使用全量并发直方图按请求权重合并窗口，P95 范围内误差不超过 max(1 ms, 5%)，超过 60 s 显式标记。

审计改为不可变事件、有界队列和单后台线程。批次满或等待目标到达后集中取出，减少逐事件唤醒；数量和预留字节限制均覆盖排队、组批、在途及重试。独立 Lettuce 连接通过稳定批次 ID 和 Lua 写入、裁剪、去重；重试和排空有预算，明确区分丢弃与结果未知。仪表盘新增审计健康面板。

现有 List 和 recent API 保持兼容，旧记录仍能读取。配置、语义和降级方式见 [运行说明](../docs/audit-and-monitoring.md)。

## 环境与口径

13th Gen Intel(R) Core(TM) i5-13500H，16 个逻辑处理器，Windows 10.0.26200，Node v24.14.0，JDK 21.0.4，Redis 7.4。发生器、上游、JVM 和 Docker Redis 共用一台主机。

每个样本使用全新 JVM（`-Xms256m -Xmx512m`）和 15 s 预热。闭环测量 30 s、并发 16；第二次重复反转场景顺序。固定到达率的在途上限为 256，并分别记录调度漏发和上限漏发。

测量前后排空审计队列，核对 `received = persisted + dropped + uncertain + pending`。所有样本最终 pending 均为 0。List 只保留最近 5,000 条，完整历史对账使用入口和确认计数；完整 ID 去重由保留全部记录的集成测试和 TCP 探针另行验证。

| 限流＋监控＋审计 | 27.2% | 185.8 | 110 | 156,640 | 22 |

仅延迟审计连接时，批次确认能力不足以匹配约 5,000 req/s 输入，触发 16 MiB 预算并以 byte_limit 拒绝新事件。断连测试触发 256 条上限（queue_full），超过重试预算的批次记为 uncertain；恢复后继续消费。两者均准确对账，业务监控仍统计全部实际请求。这是故障和超载下的显式策略。

全部 Redis 延迟时，限流器也受到影响，业务吞吐随之降低；审计仍完整确认 24,048 条，无并发发布失败。

## 真实故障、低流量与停机

- **TCP 丢响应：**独立连接确认 Redis 已写入后，让原连接的确认延迟超过客户端超时。重试 1 次后成功确认；最终 2 条记录，无重复、丢弃或未知结果。
- **低流量可见延迟：**30 个串行请求，从 HTTP 响应返回到 Redis 可见，P50 29.93 ms、P95 48.58 ms、最大 50.10 ms。20 ms 是组批等待目标，实际可见时间还包含调度和往返；仪表盘日志按 5 s 轮询。
- **正常停机：**关闭前仍有 201 条待写，约 4.76 s 后正常退出；最终保留 231/231 条，无重复。
- **强制终止：**终止前 200 条待写，最终仅保留 2/201 条，199 条未写入。内存队列和进程计数不具备崩溃恢复能力。

去重适用于同一 Redis 实例且标记有效的重试窗口；Redis 状态丢失、标记提前删除、部分写入错误不在此保证内。本轮不承诺 exactly-once 或落盘持久性。
