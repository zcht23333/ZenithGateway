# 第三轮性能与 JFR 记录（2026-09-23）

本轮提供两组独立对照和一次 GC 配置诊断。新增监控前后差约 +0.58%，依赖升级前后差约 +0.99%；每种版本只有两次未录制样本，范围重叠，不能据此宣称性能提升。所有测量保持了完整审计确认。

## 固定条件

Docker Desktop Linux VM：16 个逻辑 CPU、约 15.5 GiB 内存。固定 Microsoft JDK 21.0.12.1+1、Node 24.21.0、Redis 7.4.11 及镜像 digest。Redis、上游、网关、生成器分别使用 CPU 0–1、2–3、4–7、8–11；同一物理主机上的逻辑 CPU 分配仍受频率和宿主机调度影响。

网关容器内存上限 1 GiB，JVM 使用 `-Xms256m -Xmx512m -XX:ActiveProcessorCount=4`。每个样本启动全新 JVM，预热 45 秒，测量 60 秒；16 个连接采用闭环负载，启用限流、监控和完整异步审计。上游是固定的简短 JSON 响应，不包含真实业务处理、TLS 或大请求体。未运行构建和监控采集干扰压测。

最初未显式指定 GC，JFR 证实使用了 Serial（DefNew / SerialOld）。下列前两组使用相同原始条件；第三组才改为显式 G1。不能跨收集器、跨录制状态直接合并数据。

## 3. JFR 找到的 GC 条件差异

1 GiB 容器让默认收集器选择与常见开发机不同。[JDK 21 的 ergonomics 规则](https://docs.oracle.com/en/java/javase/21/gctuning/ergonomics1.html)说明，满足 server-class 条件时选择 G1，否则选择 Serial；这与本次录制的结果一致。

因此容器启动命令和后续基准明确指定 G1；基准在预热前使用 `jcmd VM.flags` 断言收集器，避免以后悄悄改变条件。没有同时调整堆、CPU、Netty 分配器或 Reactor 线程数。

| 约 61 秒录制 | 初始 Serial | 显式 G1 |
| --- | ---: | ---: |
| GC 事件数 | 420 | 221 |
| GC 累计暂停 | 7.051 s | 1.033 s |
| 最长 GC 暂停 | 117.412 ms | 9.118 ms |
| JFR 丢失事件 | 0 | 0 |
| 测量请求全部确认 | 393,847 | 441,839 |

| 顺序 / 版本 | 请求/秒 | P95 ms | 确认写入 | 丢弃 / 未知 |
| --- | ---: | ---: | ---: | --- |
| 01-jfr-candidate | 7363.83 | 4.787 | 441,839 | 0 / 0 |

G1 录制中的累计和最长暂停明显较小。每个收集器只有一次录制，且录制本身有开销；这是该资源条件下的诊断结果，不是通用吞吐提升承诺，也不说明 G1 在所有小容器中都最优。

Serial 录制有 3,138 个执行样本、17,082 个分配样本。高权重分配样本集中在 Netty Promise、Lettuce 队列节点、Reactor 订阅对象及字节数组；这些是进一步检查调用栈和分配率的候选方向，不能把采样权重当作精确对象分配量或堆泄漏证据。未采样到 JavaMonitorEnter 事件不代表完全没有锁竞争；Cleaner、调度器等线程的 park 时间也不能直接当作业务阻塞。

## 证据和复现

- [完整比较及 JFR 摘要](third-round-2026-09-23.json)：全部样本、JAR/JFR 校验值、环境参数及对账结果。

- 原始 JFR 和进程日志保留在本机 `.dev/third-round/profile`、`upgrade-profile`、`g1-profile`，没有提交大型录制文件或凭据。
- [既有升级报告](dependency-upgrade-2026-09-23.md)仍保留原始 Windows 结果。没有将本次不同环境的数据包装成历史回归已被彻底解释。

复验时先核对 JVM flags，再比较同一组内数据。若继续追求更高性能，应首先在目标部署条件下增加样本，并核对热点分配栈，随后再决定是否调整实现或依赖；本轮没有凭采样印象修改底层分配器或引入虚拟线程。
