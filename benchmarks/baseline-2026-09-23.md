# 第一轮性能基线（2026-09-23）

该报告来自最终成功完成的四场景运行。原始数据见 [baseline-2026-09-23.json](baseline-2026-09-23.json)，复现方式见 [README](README.md)。

## 测量条件

Windows 11（构建 10.0.26200）、Intel i5-13500H、16 个逻辑处理器、约 32 GiB 内存；Microsoft JDK 21.0.4、Node.js v24.14.0、Docker Redis 7.4。每个场景启动独立 JVM，堆参数 `-Xms256m -Xmx512m`，预热 15 秒、测量 30 秒，16 个并发 keep-alive 连接。压测器、固定响应的上游、网关及 Redis 位于同一主机。

这是一次闭环开发基线，不能作为生产容量、SLO 或优化前后提升幅度的结论。后续比较应在相同环境重复运行，并根据需要延长预热。

审计关闭时，相关统计为零，不代表该场景验证了日志可靠性。CPU 数据来自 `process.cpu.usage`，内存是按秒采样的 JVM 堆使用量峰值。

## 已确认的下一轮问题

限流加审计场景的 120647 条审计事件中，13067 条发射失败，约 10.83%；Redis 延迟场景为 1752/7920，约 22.12%。日志中的发射失败原因均为 `FAIL_NON_SERIALIZED`，即并发生产者竞争同一事件流，而不是缓冲区满。

这表明 HTTP 请求成功不代表审计记录完整。当前监控统计也订阅该审计事件流，会受到丢事件影响。下一轮应优先处理并发发射、有界队列、监控与落盘解耦及 Redis 批量写入，并以“已接收事件 = 已持久化 + 明确丢弃 + 在途事件”核对结果。

Redis 延迟场景末尾的 received、persisted、dropped 差额可能包含异步在途事件，不能仅凭差額判断持久化失败。JSON 中 `wholeRunLogCountsIncludingWarmup` 包含预热期，不能与只覆盖测量期的审计增量直接比较。
